# 数据需求与升级兼容

软件版本号不应决定 demo 是否需要重新解析。0.6.0 沿用 0.4.0 / 0.5.0 的逐场缓存 schema 3，没有为批量录像或视觉 AI 增加基础解析字段。

0.6.1 的 AI 五维评分使用已有个人回合、武器和残局统计，继续保持 demo 缓存 schema 3。统计 AI 提示词升级为版本 2，旧 AI 报告文件保留，但不会冒充新五维报告使用；新报告仅在用户点击生成时请求模型，不自动调用 API、不重新解析 demo。视觉 AI 的提示词和报告缓存保持独立。

## 已保存的数据如何复用

| 层                         | 内容                                               | 新版本的处理方式                                                                       |
| -------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 原始 demo                  | 用户指定文件夹中的 `.dem`                          | 保持原文件；仅首次导入或明确要求重新解析时运行解析器                                   |
| 本地数据库                 | 对局、玩家、回合、击杀、伤害、经济、道具及位置事实 | 复用已入库数据；数据结构变化使用迁移，不能重置数据库                                   |
| `demodata/<checksum>.json` | 每场个人指标、习惯聚合、热力图等                   | schema 3 且数据修订一致时直接读取；缺失或失效时从数据库重建该场，不能顺带重解析原 demo |
| 视频与 AI 报告             | 游戏渲染的片段、精编批次、统计点评与视觉点评       | 各自缓存和版本管理；生成或更新这些产物不使 demo 数据失效                               |

0.3.0 的缓存是 schema 2，0.4.0 将其升级为 schema 3。旧 JSON 需要重建时，基础数据库仍可复用。“重建数据文件”和“解析原始 demo”必须在界面中分别说明。0.6.0 不再升级该 schema，也不要求用户重新导入已完成比赛。

## 本轮功能实际需要什么

- 战绩和风格：玩家参赛回合、阵营、回合胜负、击杀/助攻/死亡、伤害、爆头、首杀、经济和道具事实。
- 地图习惯和 2D 复盘：按 tick 记录的位置、存活状态、水平朝向、地图楼层信息。数据库已有 `x/y/z`、`yaw`、生命值、护甲、持枪和行动状态等；这些采样不能冒充连续鼠标轨迹或精确反应时间。
- 对枪索引：击杀/伤害双方、回合、tick、武器及双方死亡 tick。对手以实际敌对事件核实，不能仅凭距离选一名玩家。
- 精编录像：原始 demo、玩家观察槽位、真实 tickrate、事件区间及死亡时间；由 CS2 渲染画面，使用已入库事实编排。增加视角不要求重新生成统计数据。
- 视觉 AI：用户选定视频的有限关键帧、对应视角/视频时间/demo tick，以及已有回合事实。视觉模型在点击后读取这些材料，不需要让 demo 解析器重跑。

## 以后增加数据的规则

1. 新增统计先检查现有数据库能否计算；能计算就只新增派生结果，不重跑原始文件。
2. 派生格式变化优先支持旧字段或逐场迁移；必须重建时只重建受影响的缓存，并保留原有可读数据。
3. 确实需要目前未保存的基础字段时，先写明缺少什么、影响哪项功能、涉及哪些比赛，再提供按需补充入口。缺少新字段的旧比赛应仍能使用已有功能。
4. 普通“解析/导入”默认跳过已入库比赛；重新解析必须使用明确标注的操作，不因更新、打开页面或更换 AI 模型隐式发生。
5. 对一次更新分别验证原始解析器调用次数、数据库内容、JSON 字节及修改时间。只验证文件夹存在，不足以证明旧数据没有被重算。

更新仍保留旧的应用标识、用户资料目录、账号与笔记键。具体路径和发布验证见 [发布说明](RELEASING.md)。

## 0.6.0 导入与空间控制

- Windows 路径按绝对路径、斜杠与大小写统一去重；`D:/...` 与 `d:\...` 不再产生两份进度。进度统计本批文件状态，并不表示重复启动了解析器。
- 已入库 checksum 默认只校验/修复缓存；只有确认框中明确勾选重新解析才重跑原始文件。被取消或移出队列的录制按 checksum 保存抑制记录，覆盖监听目录中的同场副本；旧版路径与文件指纹记录仍可读取。重启后不会被扫描器立即加入，重新选择任一副本或明确重试可恢复。
- 队列暂停会保存设置并停止开启新的解析。已经完成原始解析的资料会安全完成入库；取消原始解析只终止该任务拥有的子进程，不中断 COPY、不假称回滚。缓存生成可取消，旧缓存文件保留；取消发生在当前数据库读取安全返回之后。
- 导入提示不再遮挡已有数据。画像在整批工作结束后合并刷新；缓存失败时仍可查看成功的比赛，覆盖率按实际可读样本计算。
- 自动模式建议 2–3 个原始解析任务，入库串行以减少磁盘竞争；原手动并发数字保留，可在设置中明确选择手动值。一个真实隔离样本中，习惯缓存位置表读取从 10 次降为 1 次，所有玩家的格子、计数和证据逐项一致。交替运行耗时为旧 4.280 / 新 3.084 / 新 2.960 / 旧 3.149 秒；这是单场缓存聚合测试，不代表原始解析器普遍提速倍数。

新导入不再将装饰性鸡轨迹写入 `chicken_positions`，玩家、手雷、火焰和人质轨迹保留。现有解析器只有总位置开关，没有只关闭鸡轨迹的选项，因此解析阶段可能仍生成临时鸡 CSV；完成入库后随临时文件清理。旧库鸡轨迹不会在升级时自动删除，也没有自动执行 `VACUUM FULL` 的迁移。

数据库设置按 GiB 显示数据库和主要轨迹表（含索引）的实际尺寸；这些数值不含原始 demo、`demodata`、视频和集群 WAL。内置数据库目录来自运行中的 PostgreSQL，再用 `realpath` 解析 junction，避免把逻辑 C 盘路径误当成实际存储盘。

旧“优化数据库”的清除全部位置选项已经移除，后端拒绝旧客户端的 `clearPositions` 请求。现在“清理文件引用”只清理失效路径/未入库的 demo 元数据，不删除已入库比赛或玩家轨迹，也不承诺回收磁盘文件。删除行后的空闲页、死元组估计和可实际归还的磁盘空间并非同一数字。

后续独立空间维护流程应在确认备份、目标盘余量和数据校验后进入全局排他状态，阻止新导入、录像、数据库查询和更新；等待已拥有的操作完成，再分别执行装饰性鸡轨迹清理与保留有效玩家记录的压缩。压缩要显示不可取消阶段、失败结果和前后尺寸，不能挂在普通刷新/启动/升级上。当前版本只提供只读容量说明和保留轨迹的引用清理；实际迁移/压缩需独立维护处理。

## 未完成入库的可见性

CSV 的各张表通过独立 COPY 连接保存，`matches` 头部行存在不等于所有事实已保存。0.6.0 在本版本每次新入库前按 checksum 原子保存 `incomplete-match-imports/<checksum>.json` 标记；直到所有 COPY 都已结束、缓存失效处理完成，才删除标记。一个 COPY 失败时，也要等待其它 COPY 结束后再清理，不提前宣称取消或回滚。

带标记的比赛不能参与画像或生成缓存；同页其它已完成比赛仍可查看。入库完成会更新缓存生成代数，较早在途计算不能写回不完整缓存，最终缓存请求也不能复用较早失败的在途任务。进程中断后标记仍在，界面报告该场入库失败，需要用户明确重试；扫描器不会把部分 `matches` 行当成完成比赛，也不会悄悄重解析它。用户明确删除失败比赛时一并移除标记。这些标记只用于新启动的导入，不给历史完成比赛补标记，不使旧 schema 3 缓存全库失效。
